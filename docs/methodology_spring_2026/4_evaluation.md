# Week 5: Evaluation and Analysis Guidelines

## 1. Project Recap: What are we actually researching?

Before we dive into the evaluation metrics and how to process your logs, let's take a moment to recap the core goal of our capstone project.

Our objective is to compare a **ReAct Agent** and a **Deep Agent** for repository-level Question & Answering (QnA) and to publish these empirical findings in a scientific paper.

To achieve this, you have been running both agent architectures on the **SWE-QA dataset**, saving all execution logs, and extracting the final answers. Now, we need to analyze these logs and results using various qualitative and quantitative approaches, generate charts and tables, and prepare our findings for publication.

### The Core Research Question

Currently, the AI coding assistant market is divided into two dominant paradigms for codebase understanding:

1. **Semantic Search (RAG):** Tools like modern AI IDEs (Cursor, GitHub Copilot) pre-index your codebase into a vector database. They allow agents to use Retrieval-Augmented Generation (RAG) to find relevant code chunks via semantic search instantly.
2. **Agentic Search:** Standalone code agents that live in the terminal (such as Claude Code, Gemini CLI, OpenHands, Mistral Vibe, and DeepAgents) **do not** use RAG and do not pre-index the codebase. Instead, they rely purely on "Agentic Search," actively executing commands (like `grep`, `find`, `ls`) and reading files dynamically to navigate the workspace.

**Our main research question is to rigorously compare these two competing approaches.**

This is exactly why we strictly restricted the toolsets for each agent. The ReAct Agent represents the RAG/Semantic Search approach, while the Deep Agent represents the pure Agentic Search approach.

### Important Note on Expected Results

We **do not** have a preconceived agenda to prove that "Deep Agents are better" or that "ReAct is better." Furthermore, we are not trying to improve their core algorithmic implementations in this project. Our goal is strictly to **analyze, compare, and discover the pros and cons** of each architecture.

If your experiments show that Deep Agents get worse results while consuming significantly more tokens, **that is perfectly fine!** In fact, a negative result for Deep Agents would actually strengthen our paper rather than weaken it. It provides a fresh, data-driven insight and a strong counter-narrative against the current industry trend that heavily pushes for complex agentic search over simple RAG.

## 2. Mandatory Analysis (The Baseline)

Every group must complete the following two core analyses. These will form the quantitative foundation of your research paper.

### A. Accuracy Evaluation (SWE-QA Rubric)

You must evaluate the final answers generated by your agents using the official scoring rubric provided by the SWE-QA dataset.

- You will grade the responses based on whether they successfully retrieved the correct information and synthesized it accurately.
- **Output:** A clear comparison table showing the Pass/Fail/Partial Success rates for both the ReAct Agent (RAG or Semantic Search) and the Deep Agent (Agentic Search).

### B. Cost & Efficiency Analysis

In software engineering, accuracy alone is not enough; we must measure the cost of achieving that accuracy. Using the trace logs you saved during benchmarking, calculate and plot the following for both architectures:

- **Total Tool Calls:** The average number of tool calls required per question.
- **Token Consumption:** The average input and output tokens consumed per question.
- **Financial Cost:** Convert token usage into dollar amounts based on your chosen LLM's pricing tier.
- **The Pareto Frontier (Crucial):** Create an "Accuracy vs. Price" chart (similar to the industry benchmarks found on ArtificialAnalysis.ai). This visual will instantly show whether the Deep Agent's potential accuracy gains justify its increased token consumption compared to the baseline.

## 3. Exploratory Analysis (Free-Choice)

To make your paper unique and uncover deep insights, **each student group must select 2 or 3 additional types of analysis of their choice.** You are entirely free to design your own analysis methods.

Because you have strictly saved all the raw execution logs, you have a goldmine of data regarding *how* the AI "thinks" and searches. Below is a "menu" of highly publishable ideas you can choose from or use as inspiration:

#### Idea 1: The "Lost in the Woods" Analysis (Trajectory Length)

Do agents that take more steps (more tool calls) actually get closer to the answer, or do they just get stuck in hallucination loops?

- **Method:** Plot the number of tool calls against the Pass/Fail rate. You might discover that if a Deep Agent doesn't find the answer within the first 5 tool calls, its chances of success drop to nearly 0% due to context window pollution.

#### Idea 2: Error Taxonomy (Failure Mode Categorization)

When an agent fails, *why* exactly did it fail?

- **Method:** Sample a set of failed questions and manually categorize the logs.
  - *Retrieval Failure:* Used `grep` but searched for the wrong keyword.
  - *Context Poisoning:* Read the right file, but also read 10 irrelevant files, confusing the LLM.
  - *Synthesis Failure:* Found the exact correct lines of code, but the LLM failed to deduce the correct answer from the logic.

#### Idea 3: "Noise vs. Signal" Ratio (Context Efficiency)

Which architecture is "cleaner" in what it reads?

- **Method:** Semantic Search (RAG) retrieves specific code chunks, while Agentic Search usually reads entire files or massive `grep` outputs. Calculate the ratio of "Useful Tokens" (the actual lines of code containing the answer) vs "Total Tokens Read" during the trajectory. This proves whether Agentic Search brings in too much "garbage" context.

#### Idea 4: The "Broken Telephone" Effect (Deep Agent Specific)

Since Deep Agents use sub-agents and a planner, does information get lost when passing messages back and forth?

- **Method:** Trace the logs to find instances where the *Sub-Agent* successfully found the answer in the file system, but when it summarized its findings for the *Main Orchestrator Agent*, the orchestrator misunderstood it or dropped critical details.

#### Idea 5: Tool Usage Heatmap

What tools actually solve problems?

- **Method:** Create a breakdown of tool usage frequency. Does the Deep Agent actually use its complex planning tools, or does it basically just spam `grep` 90% of the time? This would prove if complex action spaces are actually utilized efficiently by the models.


**NOTE:** You are free to use any type of chart/table/visualization/analysis that you think may strenghten the paper.
